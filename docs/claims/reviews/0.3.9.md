Each new sentence was set against what establishes it. "Seen failing" means
the test went red when the code it names was changed, and green again when it
was restored.

- "When it does, both readings of the clock give the same answer, so the clock
  does not decide the item": `exceededIfAdmitted` counts every Receipt with a
  readable timestamp that names the object, inside the Window or out, so an

## Findings

### 1. LIMITATIONS.md, docs/RECEIPT-SPEC.md — "(draft-08)" while the repository carries -07

- Claim: "`/2` reports it as `observed-without-receipt` with reason
  `multiplicity-exceeded`, the offset and the bound (draft-08)" (also in
  `LIMITATIONS.tr.md` and `docs/RECEIPT-SPEC.md`).
- Mechanism: the published -08 text, Section 4.3.
- Why it falls short: `standards/` in this tree holds
  `draft-dogru-scitt-disclosure-evidence-07.md`, which requires `indeterminate`
  for this item. A reader who follows the citation inside the repository finds
  the opposite rule until the -08 text is added. The -08 citation itself is
  correct: the Datatracker copy states the rule, and its Implementation Status
  names 0.3.7 as not implementing it.
- Disposition: accepted; the -08 text goes into `standards/` in its own pull
  request.

### 2. LIMITATIONS.md — "The `/1` result and exit 41 do not change"

- Claim: "The `/1` result and exit 41 do not change."
- Mechanism: the change is confined to `projectResultV2`, which builds the
  `/2` body, and one line of the text report.
- Why it falls short: no test reads the `/1` body of this case, only its exit
  code. Measured instead: the case's fixtures (`before-customers-10.json`,
  `after-customers-15.json`, `receipts-customers-early.jsonl`,
  `profile-multiplicity-1.json`) through the published 0.3.8 package and
  through HEAD give byte-identical `--json` output, exit 41 for both, while
  `--json-v2` moves the item from `indeterminate`/`window-boundary` to
  `observed-without-receipt`/`multiplicity-exceeded`.
- Disposition: accepted, with the measurement stated here.
