## Findings

### 1. LIMITATIONS.md — which patterns draw on the receipts

- Claim: "every pattern on that object draws on the same receipts" (first
  draft of this release, also in `LIMITATIONS.tr.md`, `docs/RECEIPT-SPEC.md` and
  the changelog).
- Mechanism: the patterns `projectResultV2` assigns are `result.reconciled`
  only.
- Why it falls short: a pattern with an object no in-window receipt names is in
  `unreconciled` or `indeterminate` and draws on nothing, so "every pattern"
  says more than the code does.
- Disposition: reworded before `8563bc6` to name the patterns that draw, with a
  test for the case.

### 2. LIMITATIONS.md — what an item short of in-window receipts is called

- Claim: "such an item is reported as `multiplicity-exceeded`, not as a
  boundary item" (first draft, also in `LIMITATIONS.tr.md`).
- Mechanism: the reconciled branch of `projectResultV2`.
- Why it falls short: when the shortfall comes from patterns sharing
  receipts, the item is `multiplicity-shared`, not `multiplicity-exceeded`.
- Disposition: reworded before `8563bc6` to "decided by the in-window receipts
  alone, not reported as a boundary item".

### 3. LIMITATIONS.md — one receipt's bound counted once per object

- Claim: "The receipts in the window that name an object admit receipts ×
  bound statements against it" (a draft of this release, which compared each
  object's receipts with the statements on that object).
- Mechanism: a load per object, set against the in-window receipts naming
  that object.
- Why it falls short: a receipt that names two objects was counted in both
  objects' capacity. One receipt naming customers and orders, at a bound of 1,
  covered a customers statement and an orders statement, and both were
  `matched`. Reproduced with the CLI;
  `v2-multiplicity-one-receipt-two-objects` fails on that draft.
- Disposition: the code was changed before `788c641` to one budget per
  receipt, assigned as a maximum flow, and the sentences rewritten. The two
  cases where the flow errs toward `indeterminate` are stated in
  `LIMITATIONS.md`, each with a test.

### 4. docs/RECEIPT-SPEC.md — what is assigned, and when

- Claim: "Otherwise the statements are assigned to Receipts as a maximum
  flow" (a draft of this release).
- Mechanism: `boundAssignment` puts every reconciled pattern in the flow.
- Why it falls short: "Otherwise" read as if a pattern over the bound on its
  own were left out of the assignment; it is in it.
- Disposition: reworded before `8563bc6`. The same pass changed
  "beside the patterns it shares them with" in `LIMITATIONS.md`, which did not
  fit a pattern that is `multiplicity-shared` with no neighbour (the two
  limit cases), and "named by receipts that overlap", which did not say when a
  receipt is counted twice.

### 5. docs/RECEIPT-SPEC.md — which patterns the bound decides

- Claim: "A pattern whose call delta is more than bound × the in-window
  Receipts that name one of its objects is `observed-without-receipt`" (a
  draft of this release, also in `LIMITATIONS.md`, `LIMITATIONS.tr.md` and the
  changelog).
- Mechanism: the reconciled branch of `projectResultV2`, which sees only
  patterns whose objects all have an in-window Receipt.
- Why it falls short: read alone, the sentence also covers a pattern whose
  only Receipts are outside the Window: three statements against no in-window
  Receipt are more than 1 × 0, yet that pattern is a boundary item and stays
  `indeterminate` (`10,000 statements against one bound of 1 stay
  indeterminate and say the bound is exceeded`).
- Disposition: reworded before `8563bc6` to "Of the patterns that draw", and
  the `multiplicity-shared` sentences scoped the same way.
